# Phase 1 Design Ready: Real Patch Generation + Multi-file Git Data API Commit

## Goal

Replace placeholder `AI_CHANGE.txt` commits with real multi-file repository changes generated by the LLM and committed safely via GitHub Git Data API.

## Design constraints

- Keep GitHub App identity model.
- Keep no-direct-git-push primary path.
- Keep non-force branch update policy.
- Preserve deterministic fallback behavior.

## Public interface additions (design contract)

1. `PatchOp` schema

```json
{
  "path": "string",
  "action": "create|update|delete",
  "content": "string (required for create/update, omitted for delete)"
}
```

2. Commit construction interface

- `build_tree_from_patchops(repo, base_tree_sha, patch_ops) -> tree_sha`

3. Structured test report interface (for Phase 2 compatibility)

```json
{
  "attempts": [
    { "strategy_id": "string", "ok": true, "error_fingerprint": "string|null" }
  ],
  "selected_strategy": "string",
  "result": "passed|failed",
  "confidence": 0.0,
  "key_errors": ["string"]
}
```

4. `state.json` extension for future AI stop

```json
{
  "pr_controls": {
    "<pr_number>": {
      "ai_stopped": true,
      "stopped_at": 0,
      "reason": "string"
    }
  }
}
```

## Proposed implementation shape

### A. Patch proposal stage

- Add module: `ai-agent/llm/patch_llm.py`
- Input:
  - issue title/body
  - selected repo context summary
  - bounded file excerpts
  - explicit output schema contract
- Output: `PatchOp[]` only, strict JSON.

Validation rules:
- path must remain within repo root (no traversal).
- action/content consistency must be valid.
- max operations and max bytes per operation enforced.

### B. Patch application-to-tree stage (API-native)

- Add helper in `ai-agent/github/git_api_commit.py`:
  - `get_commit(repo, sha) -> commit_json`
  - `get_tree(repo, sha, recursive=False) -> tree_json`
  - `create_tree_multi(repo, base_tree_sha, tree_entries[]) -> tree_sha`
- Workflow:
  1. Resolve base commit SHA.
  2. Resolve base tree SHA from commit.
  3. For each create/update op: create blob and prepare tree entry.
  4. For delete ops: emit tree entry with `sha: null`.
  5. Create one new tree with all operations.
  6. Create commit with parent base SHA.
  7. Update branch ref (non-force).

### C. Safety and fallback

- If patch validation fails, do not commit; open/append failure report issue.
- If API call fails mid-flight, stop and emit deterministic error summary.
- Persist rejected patch metadata in state for observability.

## Acceptance criteria for Phase 1

1. Agent commits real file changes (>=1 non-placeholder file) via Git Data API.
2. Supports create/update/delete across multiple files in one commit.
3. Rejects invalid or unsafe paths deterministically.
4. No force push used in primary commit path.
5. Existing PR creation/reuse behavior remains intact.
6. End-to-end run still gated by test success.

## Test scenarios

1. Happy path multi-file update
   - Input patch includes 3 updates and 1 create.
   - One commit created with all changes.

2. Delete operation
   - Patch includes delete for existing file.
   - Resulting tree removes file.

3. Invalid path traversal
   - Patch path includes `../`.
   - Validation fails; no commit created.

4. Malformed patch JSON
   - LLM returns invalid schema.
   - Deterministic fallback; no commit.

5. Branch absent remotely
   - Agent creates branch then commits successfully.

6. API partial failure
   - Blob/tree/commit step fails.
   - No ref update; actionable error recorded.
